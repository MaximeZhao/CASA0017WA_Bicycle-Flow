# 5 人协作边界

| 人员         | 负责内容                             | 主要文件                                  | 验收                                               |
| ------------ | ------------------------------------ | ----------------------------------------- | -------------------------------------------------- |
| A 数据采集   | 来源核实、采集、定时与异常           | scripts/fetch_bikes.py、requirements.txt          | 连续采集保留多个时刻，不生成故障数量               |
| B 数据库     | 建表、数据导入、质量检查、查询与迁移 | sql/、sql/queries.sql                    | 主外键有效，重复导入不覆盖，旧表保留               |
| C 后端集成   | 数据源、参数校验、数据库接口、部署   | lib/、server.js、scripts/                 | 同一接口支持 JSON/MySQL，错误清楚，凭据不公开      |
| D 地图前端   | Leaflet/OSM、搜索、借还切换、时间轴  | index.html、assets/js/app.js、styles.css  | 经纬度正确，真实采样回放，署名可见                 |
| E 分析与验证 | 站点分析、图表、跨模块测试、交付说明 | insights.html、insights.js、tests/、docs/ | 图表对应数据库采样，空值不当成 0，另一台电脑可启动 |

共同约定 API_DATA_FORMAT.md，先锁定字段再填数据。每人测试自己的模块；E 负责跨模块验收，不是替所有人写测试。

最终演示顺序：采集 → 新快照写入 → API 查询 → 地图显示 → 切换历史 → 分析图与原始记录对应。

先完成真实站点闭环；事故数据为可选扩展，没有可信来源就保持空数组。

## 队友新上传后的职责入口

JavaScript 采集、DfT 导入、CSV 导出和原测试 API 集中在 `data-pipeline/`，原说明在 `docs/data-pipeline/`。A/B 数据同学优先从此目录核对自己的采集库；根目录 `scripts/fetch_bikes.py` 是网站模板另一套表结构的 Python 采集器，不能未经字段适配就混用。
